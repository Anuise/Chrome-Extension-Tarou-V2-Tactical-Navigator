# 戰鬥腳本協作

跟腳本作者一起把某個關卡的打法寫成戰鬥腳本 `battle-scripts/<questId>-<name>.json`，作者再從側欄頁「戰鬥腳本」匯入。名詞照 `CONTEXT.md`（關卡、戰鬥腳本、規則、操作建議、預兆、參考資料、知識庫）。

- 寫新腳本：做步驟 1–10。
- 依回饋修改既有腳本：做「修改既有腳本」，再接步驟 8–10。

全程維護一份**待確認清單**：還沒被關卡資訊 JSON 或作者親眼確認的條件值（見「條件值的來源」），以及規則依賴的行為（例如某個 buff 何時出現、何時消失），都記進去，最後交給作者在實戰中確認。

要問作者的事合併成一輪：不需要答案的部分（例如讀知識庫、寫階段大綱）先做完再問。指令輸出中的 `npm warn …`、`DEP0205` 警告與 eslint 的「Detected running in editor…」都與流程無關。

## 步驟

### 1. 轉譯參考資料

轉譯前先檢查 `reference/guide/` 的新攻略（`knowledge/guide/` 與 `knowledge/guide/nga/` 都還沒有同名 `.md` 的目錄）。來源網址（HTML 的 canonical 連結，或開頭 `saved from url=` 註解的網址）不是 NGA 或灰機 wiki 時（主機見 `scripts/tn/convert-html.ts` 的 `SITES`），先停下來問作者，並說明：轉出的知識庫會放在 `knowledge/guide/` 並被 commit，等於在這個 public repo 轉載該文章。作者同意才轉譯；不同意時，請作者先把它移出 `reference/`（留著的話每次轉譯都會轉出），打法改以作者口述為準。

在 repo 根目錄執行 `npx tsx scripts/tn/convert-reference.ts`。它只轉譯新增或更新過的參考資料，其餘跳過。印出「沒有找到任何可轉譯的參考資料」與掃描的目錄時，照「知識庫與缺資料時」找參考資料的位置。

完成條件：來源不是 NGA 或灰機 wiki 的新攻略，都已在轉譯前經作者同意或移出 `reference/`；輸出中有以「完成：」開頭的一行；每一行「略過 …」都已轉告作者並說明怎麼修正。

### 2. 確定關卡

- **關卡資訊 JSON**：作者在戰鬥中按側欄頁「戰鬥腳本」→「目前戰鬥」分頁的「複製目前關卡資訊」取得，例如 `{ "questId": "305701", "battleCount": 1, "bossName": "…", "bossBuffStatuses": ["4051", "4052_1"] }`。作者還沒貼就請他貼。要確認某個 buff 的實際 status 字串時，請他在該 buff 出現時再複製一次。作者暫時拿不到時，改用 boss 知識庫「自发链接」裡的 questId，並記入待確認清單。
- **boss 狀態卡**：「目前戰鬥」分頁上方的 boss 卡片。請作者貼 JSON 時順便看兩樣東西：計量條的紅色數字（例如顕現的破壞之力），以及預兆標籤的文字。作者在已知門檻看過的數字（例如破壞之力 50% 時顯示 50）確認 `gauge` 的刻度；作者看過的標籤文字確認該預兆的 `omen`。
- **boss 知識庫**：在 `knowledge/boss/` 搜尋 questId（灰機 wiki 的「自发链接」含 questId），找不到再搜尋 boss 名稱。

完成條件：已有 questId 與 boss 知識庫檔案；找不到知識庫時，已依「知識庫與缺資料時」告訴作者要存哪一頁。

### 3. 讀知識庫，寫出階段大綱

完整讀 boss 知識庫，包括依神意分開的小節。再看 `knowledge/guide/`（含只在本機的 `knowledge/guide/nga/`）有沒有這個關卡的攻略，問作者要依哪一份；沒有時，請作者提供他要依循的攻略文章（存法見「知識庫與缺資料時」），作者不提供時以作者口述的打法為準。

完成條件：寫出**階段大綱**給作者看：每個階段的 HP／計量條區間、預兆（原文名稱、類型、解除條件）、相關 boss buff 的 status ID；依神意（或其他玩家分組）而不同的內容分開列。

### 4. 問出戰名單

問出戰角色（主角附上職業）與召喚石。名單中的角色與召喚石沒有知識庫時，一次列出所有缺少的頁面（見「知識庫與缺資料時」），並告訴作者也可以直接口述技能的遊戲內原文與作用。

完成條件：有完整的出戰名單；沒有知識庫、作者也沒口述技能的角色與召喚石，都已列出要存的頁面。

### 5. 查技能

到 `knowledge/character/<名稱>.md`、`knowledge/summon/<名稱>.md` 查每個出戰角色與召喚石的技能原文與效果；主角的職業與 EX 技能也歸在 character 類。知識庫只有中文譯名時，請作者確認原文。作者補存頁面後回到步驟 1；作者口述的技能照作者的寫法。

完成條件：名單中每個角色與召喚石打算使用的技能，都知道遊戲內原文與作用（來自知識庫或作者口述）。

### 6. 提出打法

依階段大綱、攻略與技能，替每個階段提出打法草案（誰用哪個技能解哪個預兆、何時開奧義、何時召喚），請作者逐段確認或修改。名單做不到的解除條件，標明做不到並提出替代做法（例如減傷、換人），由作者決定。

完成條件：階段大綱的每一段都有作者確認過的打法；打法用到的每個技能都屬於名單中的角色或召喚石。

### 7. 產出草稿

照「寫規則」把打法寫成戰鬥腳本。boss 知識庫中依神意（或其他玩家分組）而不同的內容，每種各產出一份腳本。共用的階段每份都要寫：同一關卡有多份已啟用腳本時，側欄頁一次只顯示選中的那一份，由作者切換，不會重複顯示。草稿寫在 repo 外的暫存目錄（session 有 scratchpad 目錄就用它，否則用系統暫存目錄），檔名與最終檔名相同。

完成條件：每個版本一份草稿；階段大綱的每一段都有對應的規則，或作者明確表示這段不需要操作建議。

### 8. 驗證

一次驗證所有草稿：`npx tsx scripts/tn/validate-battle-script.ts "<草稿檔>" ...`。每行錯誤的格式是「檔案：欄位路徑：說明」，例如 `…：rules[2].when.hp：必須是兩個數字的區間，例如 [15, 50]`。修正後重跑。

完成條件：每個草稿都印出「：通過」，而且 exit code 為 0。

### 9. 寫入

只把通過驗證的草稿寫進 `battle-scripts/<questId>-<name>.json`（`name` 是腳本的 `name` 欄位，檔名因此對應 extension 的唯一鍵 questId + name），再對寫入的檔案依序執行：

1. `npx eslint --fix "<檔案>" ...`：統一 JSON 格式（`pnpm lint` 會檢查這個目錄）。
2. `npx tsx scripts/tn/validate-battle-script.ts "<檔案>" ...`：確認寫入的就是通過驗證的版本。

完成條件：eslint 沒有輸出任何問題，驗證 CLI 對每個檔案都印出「：通過」，兩者 exit code 都是 0。

### 10. 回報

告訴作者：寫入的檔案（完整路徑）與各自的規則數、待確認清單（逐項說明實戰時要看哪裡、看到什麼就能確認），以及匯入方式：側欄頁「戰鬥腳本」→「腳本管理」分頁 →「匯入戰鬥腳本」（可一次選多個檔案），同 questId + name 的舊版會被覆蓋；同關卡的多個版本都啟用，戰鬥中在「目前戰鬥」分頁的「腳本：」選單切換成這一場適用的版本。

完成條件：作者拿到檔案清單、待確認清單與匯入方式。

## 修改既有腳本

1. 讀作者指定的腳本（`battle-scripts/` 裡的檔案，或作者從側欄頁「腳本管理」匯出的檔案，檔名同樣是 `<questId>-<name>.json`），先用驗證 CLI 檢查一次，有錯誤就告訴作者。同時問作者這次實戰確認了哪些待確認的項目（例如看到的預兆標籤文字、計量條數字、buff 字串），一併反映到規則。
2. 讀同關卡的 boss 知識庫；回饋牽涉攻略、角色或召喚石時，也讀對應的知識庫（技能來自作者口述的，以腳本中的寫法為準）。
3. 依回饋修改，寫成草稿（位置同步驟 7）。回饋適用於多個版本時（例如共用的階段），每份都改。`questId` 與 `name` 保持不變，重新匯入時才會覆蓋舊版；必須改名時，刪掉舊檔，並提醒作者在側欄頁刪除舊腳本。改完用 `diff` 比對草稿與原檔，確認差異只有回饋要求的部分。
4. 接步驟 8–10；寫入的檔名照步驟 9。

## 寫規則

腳本結構以 `types/modules/tn.d.ts` 為準：欄位、區間、比對語意都寫在註解裡，驗證 CLI 會擋下結構錯誤。以下是型別看不出來的部分。

### 條件值的來源

側欄頁拿 upstream 已記錄的戰鬥資料比對條件：

| 欄位 | 比對的資料 | 何時算確認 |
| --- | --- | --- |
| `questId` | 關卡資訊 JSON 的 `questId`（字串） | 取自關卡資訊 JSON |
| `battleCount` | 側欄頁一律當成 1（upstream 沒有保存第幾場） | 省略這個欄位；寫 2 以上的腳本永遠不會相符 |
| `turn` | 回合數 | 一律確認 |
| `hp` | boss HP 百分比，含小數（例如 79.53） | 一律確認 |
| `gauge` | boss 獨有計量條的遊戲原始值（顕現的破壞之力），即 boss 狀態卡上的紅色數字 | 作者在已知門檻看過狀態卡上的數字（知識庫寫的是 0–100%） |
| `omen` | 預兆標籤文字的子字串。側欄頁把預兆的多個標籤以 `\|` 串成一個字串再比對，`omen` 不是「或」語法 | 作者看過標籤文字；標籤可能只有解除條件、不含預兆名 |
| `bossBuff` | boss 每個 buff／debuff 的 status 字串的前綴 | 該字串出現在關卡資訊 JSON 的 `bossBuffStatuses`；只出現在知識庫 `[status:…]` 時待確認 |

### 寫法

- 條件之間只有 AND，沒有 OR 與 NOT。「A 或 B」拆成兩條規則（兩條都成立時會重複顯示），或改用能涵蓋兩者的條件：顕現在 HP 50% 時會把破壞之力補到 50，所以「HP 50% 或破壞之力 50%」只要寫 `gauge`。
- 階段在 HP 或計量條任一方先到門檻時結束的，該階段的規則兩種條件都要寫，例如顕現第一階段同時寫 `hp` 與 `gauge: [0, 50]`；只寫 `hp` 的話，破壞之力先到 50 進入第二階段後，第一階段的規則仍會顯示。
- HP 與計量條用相鄰階段共用端點的區間，例如 `[80, 100]`、`[50, 80]`：HP 含小數，`[81, 100]` 與 `[51, 80]` 之間的 80.5% 會兩條都不成立。
- 計量條到頂後可能一直停在頂端（例如破壞之力進入第三階段後維持 100），這時前一階段的 `[50, 100]` 在後一階段仍然成立；要再用 `hp` 或 `bossBuff` 區分。
- 未確認的值寫錯時，規則可能完全不顯示。能用已確認的條件表達時就用已確認的，寧可多顯示；非用不可時，在待確認清單寫明它影響哪些規則。
- 預兆標籤文字還沒確認時，同一區間內依序出現的預兆（例如 70% 連續預兆其 1～3）合併成一條規則，操作建議依出現順序列出；作者確認標籤文字後，再拆成以 `omen` 區分的規則。
- `bossBuff` 用來區分同一階段內的狀況，例如第二階段 boss 身上是哪一種四王天類 buff。要涵蓋某個 ID 的所有後綴時寫 `<ID>_`（`4052_` 不會命中 `40521_1`）；status 本身沒有後綴時（例如 `3348`）寫完整 ID。前綴會命中所有以它開頭的 status：`3349_1` 也命中 `3349_10`，`4055_` 同時命中 `4055_1`～`4055_7`；一個前綴排除不了的，改用其他條件或拆成多條規則。
- 同時成立的規則依腳本順序全部列出：依階段先後排列，同一階段內最急的放前面。`when` 為 `{}` 的規則整場都會顯示，只留給整場通用的提醒。
- 規則不記錄觸發過沒有，每次狀態變化都重新比對。只該出現一次的操作建議（例如開場）用 `turn` 或區間限定時機。
- `note` 寫階段與原因（例如「第二階段：四王天」）。`note` 與 `text` 用繁體中文；技能名、預兆文字照遊戲原文。
- 操作建議：角色技能寫 `{ "character": "<名單中的名稱>", "skill": "<技能名>" }`，召喚石寫 `{ "text": "召喚：<召喚石>" }`，其他提醒寫 `{ "text": "…" }`。要說明技能的目的時，在它前面放一條 `{ "text": "<目的>：" }`。`character` 與 `party.characters` 用同一套名稱。
- `party` 填作者的出戰名單，只供側欄頁顯示。

### 名稱與檔名

- `name`：`<關卡簡稱> <版本>`，例如 `顕現 破壞神意版`、`顕現 再生神意版`。同一關卡的每個版本 name 都要不同：questId + name 是 extension 的唯一鍵，相同時後匯入的會覆蓋前一份。
- `name` 也是檔名的一部分，只用 Windows 檔名允許的字元（避開 `\ / : * ? " < > |`）。

## 知識庫與缺資料時

- 位置：`knowledge/<類別>/<名稱>.md`，類別為 `boss`、`guide`、`character`、`summon`。NGA 來源的攻略在 `knowledge/guide/nga/`，只留在本機。檔案開頭的 frontmatter 記錄來源 URL、站名與擷取時間。
- `reference/` 與 `knowledge/guide/nga/` 不受版本控制，只存在作者存放它們的那個目錄，git worktree 裡看不到（轉譯會印出「沒有找到任何可轉譯的參考資料」與它掃描的目錄）。看不到時問作者存放位置，直接讀那裡的知識庫；要轉譯新的參考資料，請作者存進目前目錄的 `reference/`。
- 標記：`[status:<ID>,… <名稱>]` 是 status 圖示，多個 ID 代表輪播組（例如六屬性各一）；`[架势技]`、`[咏唱技]` 是預兆類型；`[img:說明]` 是其他圖片。灰機 wiki 以簡體中文撰寫，預兆名與 buff 名多半保留日文原文。
- 缺資料時，一次列出所有缺少的頁面，每項寫明類別、哪一頁、存放目錄，並附上存法：
  1. 用 Chrome 開啟該頁（boss、角色、召喚石用灰機 wiki 的對應頁面；攻略用作者要依循的文章，NGA 與灰機 wiki 以外的來源轉譯後會被 commit，見步驟 1），「另存新檔」，存檔類型選「網頁，完整」。
  2. 存進 `reference/<類別>/<名稱>/`，每個目錄只放一個 HTML 與它的 `_files` 目錄。`<名稱>` 會成為知識庫檔名：boss 用關卡名，角色與召喚石用名單中的名稱，攻略自訂。
  3. 回到步驟 1 執行轉譯。

  `reference/` 只留在本機，轉譯指令會確保它被 `.git/info/exclude` 排除。
